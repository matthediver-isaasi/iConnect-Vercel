# iConnect Sales Pipeline, Commercial Products, Quotations & Event Ticket Allocations

## Replit Build Scope

# 1. Objective

Introduce a new **Sales** module into iConnect focused on organisation-to-organisation commercial activity, particularly:

* Sponsorship packages
* Partnership packages
* Exhibition space
* Advertising
* Speaker/session opportunities
* Event-related commercial packages
* Corporate ticket purchases
* Other commercial products and services

The module should manage the commercial journey from:

**Organisation → Opportunity → Quote → Sale → Invoice**

while reusing iConnect's existing:

* Organisation CRM
* Member/contact records
* Events
* Event ticket types
* Event registration engine
* Authentication
* Permissions
* Notification systems
* Document/file storage
* Xero integration where already available

The module must **not** become an accounting system or create a second event registration system.

Xero/QuickBooks remain responsible for accounting.

The existing iConnect Event Registration engine remains responsible for named delegate registration.

---

# 2. Critical Architecture Principles

## 2.1 Organisation remains the master customer record

Do not create a separate Sales customer database.

All Sales Opportunities must link back to an existing Organisation record.

Reuse existing Organisation data including, where applicable:

* Organisation name
* Address
* Billing address
* Contacts
* Members
* Custom fields
* Website/domain
* Telephone
* Existing notes
* Existing external accounting references

Commercial activity should ultimately become part of the Organisation's CRM history.

---

## 2.2 Opportunity and Quote are separate entities

Do not use a Quote as the Sales Opportunity.

The relationship should conceptually be:

**Organisation**

→ **Opportunity**

→ **Quote**

→ **Quote Version**

→ **Quote Lines**

→ **Sale**

→ **External Accounting Invoice**

One Opportunity may therefore have:

* Multiple discussions
* Multiple quote versions
* Different package combinations
* Price negotiations
* Different customer contacts

before becoming a completed sale.

---

## 2.3 Event ticket allocation and delegate registration are separate

This is a critical requirement.

A commercial sale may include Event Tickets even though delegate information is not known at the time of sale.

Therefore:

**Ticket Allocation = ownership of event capacity**

**Registration = named attendee**

These must remain separate concepts.

Commercially purchased capacity must reduce event availability when the sale is confirmed.

Named delegates may then register later using the existing Event Registration engine.

Do not build a second commercial event registration engine.

---

# 8. Group Ticket Capacity

Inspect the existing handling of Group Tickets.

Commercial ticket allocation must support cases such as:

**1 × Group Ticket**

where:

**1 Group Ticket = 10 delegate places**

Event capacity calculations must use the underlying number of delegate places and not simply the number of commercial quote lines.

Conceptually each Ticket Type needs to expose or derive:

**delegateCapacityPerTicket**

Example:

Standard Ticket:

1 ticket = 1 delegate

Group Ticket:

1 ticket = 10 delegates

If an equivalent mechanism already exists, reuse it.

# 35. Event Inventory Rules

Event availability must incorporate commercial allocations.

Conceptually:

**Available Delegate Capacity**

=

**Event/Ticket Capacity**

minus

**existing direct booked capacity**

minus

**confirmed commercial allocated capacity not already represented by those direct bookings**

minus

**other valid holds/reservations**

The exact calculation must be adapted to the existing iConnect Event architecture.

Do not simply add another independent counter if that introduces the possibility of double counting.

---

# 36. No Double Consumption

This is critical.

If 6 Event Ticket places were consumed when the commercial sale was completed:

Capacity must **not decrease again** when the six named delegates subsequently register.

The Registration must consume the Organisation's allocation rather than general inventory.

This behaviour should be transactionally safe.

---

# 37. Capacity Transaction Safety

The sale of the final available Event places must be concurrency safe.

Example:

Event has 4 remaining places.

Salesperson A tries to sell:
4 places

At the same time Salesperson B tries to sell:
4 places

Only one transaction must succeed.

Use database transactions/locking or the appropriate Supabase/Postgres mechanism.

Never trust capacity calculations performed only client-side.

---

# 38. Quote Stage vs Inventory

Do not consume Event inventory merely because a Quote is:

* Draft
* Sent
* Viewed

Inventory is consumed when the commercial sale becomes confirmed.

Optional temporary reservations may be introduced separately.

* Indexes

# 74. Event Ticket Snapshot vs Reference

The commercial Quote should preserve what was sold while the Allocation should still reference the real Event/Ticket Type.

Therefore retain both:

* Ticket Type reference
* Relevant quote-time snapshot description/price/capacity

Be careful if an Event administrator later edits or removes a Ticket Type.

Do not allow historic allocations to become orphaned or lose meaning.

# 77. Capacity Conflict Handling

If a Quote contains Event Tickets and there is no longer sufficient availability at acceptance time:

Do not oversell.

Tell the salesperson/customer that availability has changed.

Require intervention before confirming the sale.

This is particularly important because Quotes may remain open for weeks.

# 95. Replit Agent Instruction

Before coding the Event Allocation element, inspect the existing Event architecture and document internally how:

* Event capacity is currently calculated
* Group Tickets currently consume capacity
* Registration records are created
* Payments are calculated
* Ticket Types are selected
* Complex Event registration operates
* Invitations work
* Sessions/workshops are allocated
* Cancellations restore capacity

Then introduce Commercial Ticket Allocations as an additional legitimate source of capacity ownership.

Do not redesign existing Event Registration simply to accommodate Sales.

The intended model is:

**Commercial Sales acquires the entitlement.**

**Existing Event Registration converts that entitlement into named attendees.**

# 96. Definition of Success

The feature is successful when an iConnect tenant can:

1. Create commercial Products.
2. Build sponsorship/partner Bundles.
3. Include Event Tickets within those Products/Bundles.
4. Create a Sales Opportunity against an existing Organisation.
5. Assign a salesperson and contacts.
6. Build a Quote from Products, Bundles and free-text lines.
7. Revise and send the Quote.
8. Mark/accept the sale.
9. Immediately consume any included Event Ticket capacity.
10. Allow the Organisation to supply delegate information later.
11. Register those delegates through the existing Event Registration engine.
12. Prevent Event overselling.
13. Track the commercial relationship against the Organisation.
14. Convert the completed sale to Xero or QuickBooks.
15. Report on pipeline, won revenue, Event commercial performance and Event Ticket allocations.

The finished capability should feel like a natural extension of iConnect's existing Organisation and Event functionality rather than a separate CRM product bolted onto the platform.
