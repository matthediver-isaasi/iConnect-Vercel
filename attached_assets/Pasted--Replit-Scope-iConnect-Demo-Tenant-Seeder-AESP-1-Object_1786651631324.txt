# Replit Scope — iConnect Demo Tenant Seeder: AESP

## 1. Objective

Build a reusable demo-tenant seeding capability for iConnect, beginning with a fully populated fictional professional membership organisation:

**AESP — Association of Environmental & Sustainability Professionals**

This must not simply create a tenant with a few dummy users. The objective is to create a convincing, populated membership organisation that can be used for:

* sales demonstrations;
* development/testing;
* screenshots and marketing;
* staff training;
* testing reporting and dashboards;
* demonstrating realistic workflows;
* demonstrating different membership states and edge cases.

AESP is the first of three planned demo tenants.

The seeding architecture must therefore be generic enough that subsequent demo organisations can be defined using configuration/data rather than requiring another one-off implementation.

---

# 2. Important First Step — Audit Existing iConnect Architecture

Before implementing anything, inspect the existing iConnect database schema, models, APIs and tenant architecture.

Identify the existing entities used for:

* tenants;
* tenant branding/settings;
* users;
* contacts/members;
* organisations/employers;
* membership types;
* memberships/subscriptions;
* membership applications;
* FormBuilder forms;
* groups;
* committees;
* roles;
* events;
* event registrations;
* payments/invoices;
* communications/preferences;
* documents/resources;
* surveys;
* CPD;
* mentoring;
* website/CMS content;
* audit history.

**Do not create parallel tables where an appropriate iConnect entity already exists.**

Map the seed data into the existing iConnect structures.

Where a feature described below does not yet exist in iConnect, do not invent an unrelated subsystem purely for the demo. Either:

1. omit that part of the seed data cleanly; or
2. seed it into the relevant existing generic structure where appropriate.

Document any such omissions in the implementation summary.

Create a reusable demo tenant seeding framework.

```text
        organisations

        committees
        events
```

The exact implementation should follow the existing project architecture.

The key principle is:

> Demo tenant definitions should be data/configuration driven wherever practical.

Future demo tenants must be able to reuse the same seeding mechanism.

---

# 4. Seeder Safety

This functionality must be safe.

## Requirements

The seeder must:

* only operate against the explicitly selected tenant;
* never affect another tenant;
* never modify production customer data;
* be idempotent where practical;
* use stable demo identifiers/keys;
* avoid duplicating records every time it runs;
* support complete deletion/reset of the AESP demo data;
* clearly distinguish demo-generated data from real data.

Where appropriate add metadata such as:

```text
is_demo = true
demo_seed = "aesp-v1"
```

If the existing schema does not support metadata of this nature, use an appropriate existing mechanism rather than making invasive schema changes solely for this purpose.

# 11. Membership Statuses

The seed dataset must include members in different lifecycle states.

Include examples of:

* Active
* Pending application
* Awaiting approval
* Awaiting payment
* Recently renewed
* Renewal due shortly
* Renewal overdue
* Lapsed
* Cancelled
* Retired
* Recently upgraded
* Application rejected/declined, if the existing system supports this

Suggested proportions:

* approximately 75% active/current;
* 5–10% renewal approaching;
* 5% overdue;
* several pending applications;
* several lapsed;
* several historical/cancelled records.

This is important because a demo database containing 100 perfectly active members does not realistically demonstrate the platform.

# 12. Dates

* Student joined this year;
* recently lapsed member;
* member renewed yesterday;

* overdue member;

Dates should be calculated relative to the seed/run date where practical so the demo does not become obviously stale.


# 38. Data Quality / Realism Rules

Demo data must feel human.

Avoid patterns such as:

```text
Member 001
Member 002
Member 003
```

Avoid:

* sequential identical joining dates;
* identical addresses;
* identical employers;
* every member attending every event;
* every invoice being paid;
* every application being approved;
* every member opting into everything.

Introduce realistic variation.

However, generation should remain deterministic enough that recognised demo personas do not change every time the database is reseeded.

---

# 39. Deterministic Seeding

Use a fixed random seed or equivalent deterministic approach.

This means:

* Sarah Mitchell remains Sarah Mitchell;
* her membership remains MAESP;
* dashboard numbers remain broadly predictable;
* screenshots remain reproducible;
* demonstrations can use documented personas.

Randomisation can be used for filler records but should be deterministic.

---

# 40. Reset Behaviour

The reset/reseed process must:

1. identify records owned by the AESP demo seed;
2. remove those records safely;
3. preserve anything outside the demo tenant;
4. rebuild the AESP dataset;
5. report success/failure clearly.

Do not assume IDs remain the same after reset unless the existing system architecture makes that safe.

Stable lookup keys should be used where demo scripts depend on particular personas.

---

# 42. Performance

Initial seed target:

**approximately 120 members**

However, design the generator so we can later request:

```text
Small: 120
Medium: 1,000
```

without rewriting the seed engine.

The 6,500 figure is useful for future realistic scale/performance testing but should not be the default seed.

# 43. No External Side Effects

Demo creation must NOT:

* send welcome emails;
* send renewal reminders;
* trigger SMS;
* send WhatsApp;
* send RCS;
* charge Stripe;
* create live GoCardless mandates;
* trigger external webhooks;
* send third-party integrations real data.

Use existing suppression/test flags where available.

This requirement is critical.

---

# 45. Acceptance Criteria

The task is complete when:

* AESP can be created as a complete tenant from the demo seeder;
* approximately 100–150 realistic members exist;
* five membership grades exist;
* multiple membership lifecycle states exist;
* fictional organisations/employers are populated;
* known demo personas exist;
* groups and committees are populated;
* historical and future events are populated;
* event registrations contain varied states;
* payments/subscriptions contain realistic history where supported;
* the tenant's dashboards contain meaningful values;
* CMS/content areas are not obviously empty where supported;
* no lorem ipsum exists;
* no real personal information is used;
* no external emails/messages/payments are triggered;
* the seed operation cannot modify another tenant;
* the tenant can be safely reset and reseeded;
* the implementation is reusable for future demo tenants.

# 46. Architecture Requirement for Future Tenants

Do not hard-code the demo framework specifically around AESP terminology.

The next planned tenants will be fundamentally different:

### British Classic & Heritage Motoring Club

An enthusiast/community membership organisation with individual, joint and family membership, regional groups and events.

### Independent Hospitality Network

A B2B trade association where the organisation/business is the principal member and multiple individuals belong beneath each organisation.

The seed architecture must therefore support:

```text
Person-centric professional membership
Community/family membership
Organisation-centric corporate membership
```

without requiring three separate seeding systems.

AESP is simply the first implementation of that framework.
