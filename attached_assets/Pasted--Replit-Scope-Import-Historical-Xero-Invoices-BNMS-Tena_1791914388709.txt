# Replit Scope: Import Historical Xero Invoices – BNMS Tenant

We need to introduce the ability to import historical invoices against individual member records within the **British Nuclear Medicine Society (BNMS)** tenant in iConnect.

The spreadsheet contains over 9,000 historical invoice entries, including Xero invoice numbers. These should be imported and made accessible to both administrators and members without unnecessarily consuming our Xero API allowance.

## 1. Import Requirements

- Import data exclusively from the worksheet named **"To import good"**.
- Use the spreadsheet columns to map each invoice to the appropriate member record.
- Preserve the invoice details supplied in the spreadsheet, including the Xero invoice number and any associated dates, amounts, descriptions or statuses.
- Ensure imported invoices are correctly associated with the BNMS tenant and cannot be accessed by other tenants.
- Do not create duplicate invoices.

**Important: Existing invoice records must take precedence.**

If an invoice already exists against a member record in iConnect (particularly invoices generated through the existing membership payment functionality), it must not be overwritten, replaced or duplicated by the historical import.

The import should identify these existing records and skip them, preserving all existing invoice data and relationships.

## 2. Displaying Historical Invoices

Imported invoices must be visible in two locations:

**Administrator view – `/members`**
- Display historical invoices within the member's existing Activity tab.
- Clearly identify the invoice number, date, amount and status where available.
- Allow administrators to select an invoice to view or download the original Xero invoice.

**Member view – `/history`**
- Display imported invoices alongside existing membership and transaction history, ideally using the existing Membership tab.
- Members should be able to view their historical invoice details.
- Selecting an invoice number should provide access to the original Xero invoice for viewing or downloading.
- Members must only be able to access invoices belonging to their own records.

Ideally, historical invoices should appear alongside existing invoice records without creating a separate or inconsistent interface.

## 3. Xero Integration – Lazy Loading Is Essential

**We must not make any Xero API calls to validate or retrieve invoices during the import process.**

With over 9,000 historical records, attempting to validate every invoice against Xero would unnecessarily exhaust our API allowance.

Instead:

1. Import the invoice metadata directly from the spreadsheet.
2. Store the Xero invoice number as the reference for future retrieval.
3. Do not contact Xero during import or when displaying invoice lists.
4. Only request the original invoice from Xero when an administrator or member explicitly clicks an invoice number to view or download it.
5. Where practical, cache the successfully resolved Xero invoice ID against the imported record to avoid repeated lookups.
6. Handle missing or inaccessible Xero invoices gracefully, without affecting the historical record in iConnect.

Please check whether the existing Xero integration supports retrieving an invoice by its invoice number, or whether an initial lookup is required to obtain the internal Xero invoice ID before downloading the PDF.

Any such lookup must happen **only when the specific invoice is requested**, never as part of the bulk import or normal page loading.

## 4. Duplicate Detection and Data Protection

We need particular care around historical invoices already represented within iConnect.

Please review how invoices are currently stored and linked to membership payments before designing the import.

The import must:

- Check for existing invoices using the appropriate tenant, member and invoice identifiers.
- Avoid overwriting existing invoices, payment references or membership relationships.
- Avoid creating duplicate entries if the import is accidentally run more than once.
- Prefer existing iConnect records wherever a matching invoice is identified.
- Preserve all existing member activity and transaction history.

Matching should not rely on invoice number alone if the current data model requires additional identifiers.

## 5. Import Validation and Reporting

Before committing the import, provide a preview containing:

- Total spreadsheet rows identified.
- Records successfully matched to members.
- Records where no matching member could be found.
- Invoices already present in iConnect that will be skipped.
- Duplicate entries within the spreadsheet.
- New invoices eligible for import.

Any unmatched or problematic records should be available for review rather than silently discarded.

Once completed, provide an import summary showing the number of invoices created, skipped and rejected.

This validation must be performed against **iConnect's database and the spreadsheet only**, without making Xero API requests.

## 6. Technical Considerations

Please review the existing invoice, membership payment and Xero integration architecture before implementing changes.

Where possible, reuse the existing invoice model and display components rather than introducing an entirely separate historical invoice system.

The solution should also:

- Support safe processing of 9,000+ rows without request timeouts.
- Be idempotent, allowing the same file to be imported again without duplication.
- Maintain tenant isolation and existing RBAC permissions.
- Ensure Xero API calls happen server-side, with no credentials exposed to the browser.
- Avoid triggering any payment collection, invoicing, accounting sync or membership renewal processes.
- Treat imported invoices as historical records, not newly issued invoices.

2. Whether our current invoice data model can accommodate historical invoice entries without disrupting existing membership invoices.
3. How existing invoices can be reliably detected and preserved.
4. Whether Xero invoice PDFs can be retrieved on demand using the invoice number supplied.
5. Whether the existing Activity and History interfaces can display imported invoices without significant restructuring.
6. Any technical limitations, data inconsistencies or potential risks.

Please provide your findings and proposed implementation approach before proceeding with the development.
