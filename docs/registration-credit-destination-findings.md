## Bounded provider reads (same date)

The tenant's DEST `tenant_integrations` shows enabled Stripe and Xero integrations; Stripe events mode is `live`. A destination-pinned subprocess remapped only the runtime Supabase URL/service key to DEST *before* importing the existing `getStripeCredentials(tenant, 'events')` resolver. With the resolved key held in process memory (never printed), it made **only** `paymentIntents.retrieve` and paginated `refunds.list` calls for the seven distinct event intents. **7/7** identity-matched intents were `succeeded`; combined `amount_received` was **GBP 690.00** (69,000 minor units), matching the card booking `total_cost` sum. All **7/7** refund enumerations ended with `has_more=false`, **zero refunds** were returned (any status), and there were **zero** provider/identity/pagination failures. No refund operation or evidence persistence was attempted. This proves no Stripe refunds *on those seven specific intents at lookup time*, not that a refund was owed or that other payment references are covered.

For Xero, **27/27** distinct linked invoices were identity-matched via read-only `GET /Invoices/{id}` using the already-valid tenant token, without invoking `getXeroInvoice`: the existing helper calls `getValidXeroAccessToken`, which **can refresh/rotate and persist a token**, violating this audit's zero-write boundary. The subprocess required the token to have >5 minutes remaining before each GET, never refreshed it and did not expose it. Results: **26 PAID, 1 AUTHORISED**; **one** account-payment, single-row group's invoice had **GBP 60.00 AmountCredited** and one linked credit note. A read-only `GET /CreditNotes/{id}` identity-matched the note: `PAID`, GBP 60.00 total, zero remaining credit, one allocation to that invoice, zero note refunds. The affected invoice was `PAID` with GBP 60.00 total, GBP 0.00 amount paid, GBP 60.00 credited and GBP 0.00 due. This **real Xero credit is absent from booking credit-note IDs and reversal-evidence rows**; absence of those DB links was not absence of provider credit. Invoice-linked discovery does **not** enumerate unallocated/otherwise unlinked credit notes, so it cannot certify the entire Xero scope empty. No credit-note creation/allocation or DB persistence was attempted.

**Backend handoff for a complete-empty verifier:** Treat the 7 Stripe intents as fully enumerated *per reference*, but never infer all-provider emptiness from them. Reconcile the existing GBP 60 Xero note against its invoice/group with provider ID, allocation, amount, currency, status, identity and attribution checked before recording evidence; preserve the distinction between an invoice credit and a card refund. For an `empty_verified` conclusion, cover **all applicable payment/accounting scopes**, enumerate complete provider pagination and unlinked/unallocated accounting credits where supported, resolve invoice/group attribution, and record exact per-scope verification time/coverage and any errors durably. The 37 fully-covered groups have no invoice/intent reference: explicitly establish whether provider scope is inapplicable instead of calling a missing reference an empty read.
