---
name: Financial dry-run boundaries
description: Why financial previews must share orchestration and stop at unperformed effect results.
---

Keep financial dry runs on the actual scheduled processing path, not a separately maintained prediction engine. Do not invent a successful claim or provider response to make a trace more complete.

**Why:** The user explicitly requires production fidelity with zero business mutations. In this system, apparently read-only helpers have historically reached singleton clients and hidden writes; injecting only the top-level database is insufficient. An incomplete but explicit effect-dependent continuation is safer than a confident forecast based on fabricated state.

**How to apply:** Preserve capability-only transitive imports and deny-by-default read adapters when extending processing. Evaluate independent jobs against their own current evidence, retain concrete conditional continuation descriptions, and keep global scheduling eligibility distinct from per-plan eligibility.

For approved historical data repairs, distinguish between-phase approval checks from within-transaction preservation checks.

**Why:** Ordinary portal activity by an unrelated member changed a whole-tenant before-image hash between a successful dry run and application. Blocking that activity is not necessary to protect the approved cohort.

**How to apply:** Pin the approved members, all their relevant state, proposed rows and provider evidence across phases; revalidate shared configuration and DD evidence under locks. Within each transaction, continue comparing the broader protected records before and after to catch unintended writes. Never ignore changes to an approved member merely because an unrelated activity field can also change.
