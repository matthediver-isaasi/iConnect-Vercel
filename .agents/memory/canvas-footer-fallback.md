---
name: Reusable Canvas footer fallback
description: Source and fallback semantics for reusable Canvas footer assignments.
---

Footer source selection is explicit and legacy configuration remains stored when switching modes. A microsite in inherit mode must use the main site's configured footer unchanged, not merge in its retained microsite override. A microsite in configured mode uses its retained override, and an unavailable Canvas selection falls back to the effective configured footer. Reusable footers carry a main-site or microsite authoring context; creating a microsite footer assigns it atomically, while duplication preserves context without replacing the live assignment. Tenant and microsite reads must retry without the optional Canvas-footer columns when PostgreSQL or PostgREST reports those specific columns as missing.

**Why:** Retaining dormant configuration makes mode switching reversible, but blindly merging it would make “inherit” render a stale microsite override and violate the admin's explicit choice. Explicit authoring context lets Canvas expose the correct scoped typography, CTA styles, and palette. Preview environments can temporarily run application code ahead of the reusable-footer migration; selecting the new columns before resolving the tenant otherwise makes the entire site appear tenantless and hides a valid configured footer.

**How to apply:** Any public, SSR, preview, or editor path resolving footer chrome must interpret the source mode before merging configuration and must validate Canvas ownership before returning a design. Microsite-scoped creation requires microsite-management authority in addition to Canvas editing access. Schema fallback must be narrow: retry only when the reported missing column is one of the optional footer columns; do not hide unrelated database failures.
